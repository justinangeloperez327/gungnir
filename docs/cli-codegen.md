# CLI and Code Generation

> **Status: Gungnir 1.0 current contract.** Generated applications use the structured compiler. Native extension hooks remain C++.

| Command | Purpose |
| --- | --- |
| `gungnir new <name> [path]` | Create a structured project, routes, view, environment files, and editable bootstrap |
| `gungnir build [--release]` | Validate modules/routes and build native executables with CMake |
| `gungnir run [--release]` | Build and run; propagate build/application exit codes |
| `gungnir dev` | Watch, rebuild, and restart with diagnostics |
| `gungnir make:model <name>` | Model in `app/models` |
| `gungnir make:controller <name>` | Controller in `app/controllers` |
| `gungnir make:middleware <name>` | Async middleware in `app/middleware` |
| `gungnir make:migration <name>` | Migration in `database/migrations` |
| `gungnir make:request <name>` | Typed `validate<Name>Request(Request)` function in `app/requests` |
| `gungnir make:job <name>` | Serializable job in `app/jobs` |
| `gungnir make:event <name>` | Event in `app/events` |
| `gungnir make:mail <name>` | Mail composer in `app/mail` |
| `gungnir make:listener <name> <module::Event>` | Listener for an existing event |
| `gungnir make:policy <name> <module::Model>` | Policy for an existing model |
| `gungnir make:notification <name> <module::Model>` | Database notification for an existing model |
| `gungnir migrate[:rollback\|:reset\|:status\|:plan] [--release]` | Apply, undo, inspect, or plan migrations |
| `gungnir lsp` | Run the stdio [language server](editor-tooling.md) |

For example:

```sh
gungnir make:event UserCreated
gungnir make:listener RecordUser app.events.UserCreated::UserCreated
gungnir make:model User
gungnir make:policy User app.models.User::User
```

Generators refuse to overwrite files. Declaration-based generators preserve PascalCase filenames that match the generated type, such as `User.gnr`, `UserController.gnr`, and `AuthMiddleware.gnr`. Migrations keep snake_case filenames such as `create_users_table.gnr`. Generated `.gnr` uses documented framework declarations, typed functions, and arrow callbacks. Request helpers are validation functions, not a new request class syntax. Import the helper's module and call `validateStoreUserRequest(request)`.

## Project bootstrap

`.gungnir-project` contains `name=...` and `profile=structured`. Projects without a profile keep the compatibility build and their existing model/controller/middleware/migration generators. Migrating a project requires converting its declarations before adding the structured profile.

`bootstrap/app.hpp` is editable and never regenerated by builds. `bootstrap::configure(Application&)` adds adapters, providers, bindings, and middleware. The supplied bootstrap uses in-memory cache, queue, and mail, plus local storage; replace these for persistent production services. Database notification support is enabled when a database is configured. Native database adapters exported by the installed package are linked and registered. Database selection still comes from configuration.

Generated bootstrap installs container factories for controllers, middleware, listeners, and policies, honoring explicit bindings. It registers middleware aliases by their unique declaration name. Listeners, policies, and job handlers register during application boot, followed by `bootstrap::boot(Application&)`. That hook can add schedules or further registrations. Workers and schedulers require explicit startup. Declarations requiring constructor values need a factory in `configure`; dependencies marked `inject` use generated factories.

All structured `.gnr` modules are compiled except `routes`, `.gungnir`, `.git`, `build`, `vendor`, and `storage`. Routes retain `Route::get("/", HomeController::index)` syntax and are checked against the declarations. Unique type names have native aliases for routes/bootstrap; ambiguous names must be qualified in native hooks. Application and migration executables share the same generated module library. Migration planning does not boot a database connection.

`GUNGNIR_CMAKE_PREFIX` supplies an installed package prefix. CMake must be available on `PATH`. On MSVC, generated applications use the dynamic runtime expected by the installed Gungnir package in development builds, so `gungnir build`, `gungnir run`, and `gungnir dev` remain link-compatible with release-installed framework libraries. Builds retain unchanged generated files and native objects; see [modules](modules.md).

## Development watcher

`dev` watches source, native headers, bootstrap, `.env`, configuration, and views. It polls at 200 ms and waits for a stable snapshot before rebuilding. A failed build leaves the last healthy application running. A successful build replaces it with a new executable. Ctrl-C stops and reaps the application. This is a process restart; in-memory state is lost. Generated output, storage, and vendor/build directories are excluded.

## Validation

The PR gate compiles public headers in isolation, runs compiler/tooling tests, and installs the framework to compile and run a generated project. The generated-app test covers every generator, injection, listeners/policies/jobs, HTTP, incremental rebuilds, migrations, and the POSIX watcher lifecycle. External database/Redis/TLS service jobs remain on pushes to `main`. Tests keep assertions enabled in Release builds.
