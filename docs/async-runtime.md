# Asynchronous Runtime and Networking

Gungnir's application language hides C++ coroutine mechanics, but the runtime must still provide genuine scheduling semantics underneath `async` and `await`.

Group 5 introduces the runtime primitives used to move away from inline coroutine completion and blocking-only execution:

- `Task<T>` remains the coroutine result abstraction generated by the language frontend.
- `Executor` owns a bounded worker population and schedules ordinary work or suspended coroutine handles.
- `CancellationSource` and `CancellationToken` provide cooperative cancellation state.
- `sleep_for` provides an awaitable timer foundation.
- `Backpressure` provides admission accounting for bounded runtime resources.

The HTTP/1.1 listener now uses a non-blocking readiness reactor for listener/client sockets, connection state, limits, timeouts, keep-alive, and graceful draining. Route tasks are still completed inline only when they do not genuinely suspend. The next transport/runtime integration must schedule suspended handler continuations without returning to blocking socket workers or exposing coroutine machinery to application code.

## Runtime rules

Application code should use Gungnir `async` and `await`, not `co_await` or `Task<Response>`.

A coroutine suspension must represent real asynchronous work. Synchronous database or filesystem calls are not relabeled asynchronous merely for API appearance.

Cancellation is cooperative. Components should check cancellation before expensive work and at suspension boundaries.

Backpressure belongs at resource boundaries such as accepted connections, queued work, streams and database operations. Unbounded queues are not an acceptable production runtime design.

Graceful shutdown should stop accepting new work, signal cancellation where appropriate, drain accepted work within configured limits, then release runtime resources.
