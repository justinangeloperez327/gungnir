# ORM Relationships

Gungnir model relationships are explicit model members whose metadata is generated by the language/compiler layer.

Supported relationship shapes:

- `HasOne<T>`
- `HasMany<T>`
- `BelongsTo<T>`
- `BelongsToMany<T>`
- `HasOneThrough<T, Through>`
- `HasManyThrough<T, Through>`

## Eager loading

```cpp
auto users = User::with({"profile", "posts.comments"}).get();
```

Gungnir batches relationship keys during eager loading. It does not execute one relationship query for every parent model.

## Loaded state

Relationships distinguish **not loaded** from **loaded but empty**. Accessing an unloaded relationship throws `RelationNotLoaded` rather than silently issuing hidden database work.

This is intentional: Gungnir does not implement implicit lazy loading by default because hidden queries make N+1 problems difficult to detect.

Single relationships support direct pointer-like access after loading:

```cpp
user.profile->display_name;
```

Many relationships are iterable and expose `first()`, `size()`, `empty()`, and `get()` after loading.

## Many-to-many

`BelongsToMany` stores explicit pivot table and key metadata. Eager loading first resolves the pivot rows, then loads related models in a batch.

Pivot mutation operations such as attach, detach, and sync require a database mutation contract and should not be simulated merely by modifying the in-memory relation state.

## Through relationships

Has-one-through and has-many-through relationships resolve the bridge models in batches and then resolve related models from the bridge keys.

## Polymorphic relationships

Polymorphic relationships are not declared as supported yet. They require a stable morph-type identity strategy and eager-loading implementation; adding only type names to the public API would create a misleading partial feature.
